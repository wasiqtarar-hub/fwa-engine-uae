# The demo datasets

The app ships three claim files. All figures on any page describe whichever one is loaded.

| File | What it is | Checks that can run |
|---|---|---|
| `data/uae_demo.zip` (default; also `data/uae_demo/`) | **SYNTHETIC** multi-table UAE-style dataset, AED | **163 of 164** |
| `data/claims_demo_synthetic.csv` | **SYNTHETIC** claim-header file (below) | 37 of 164 |
| `data/claims.csv` | sample claim-header extract | 37 of 164 |

## The UAE multi-table demo (`data/uae_demo.zip`)

> **SYNTHETIC.** Generated by `tools/make_uae_demo_dataset.py` to exercise the engine. No row
> describes a real person, provider, payer or claim. **A check that passes on data built to pass
> it is a test of the check, not evidence that it detects fraud.** Nothing measured on this file
> transfers to real claims.

| | `uae_demo.zip` |
|---|---|
| Claims · lines | 24,855 · about 62,000 (Jul 2024 – Dec 2025, 18 months) |
| Members · providers · agents | about 9,000 · 244 (hospitals, clinics, pharmacies, labs, radiology) · 45 |
| Tables | the 17 canonical tables plus about 40 operational and reference tables |
| Claim mix | outpatient 12,855 · pharmacy 5,787 · lab 3,153 · inpatient 1,910 · radiology 1,150 |
| Planted claims (answer key) | 2,627 across 8 families |
| Checks that can run | **163 / 164** (77 fully, 86 in a simplified form); 157 raise at least one flag; 0 errors |
| Engine run time | about 2 minutes |
| Models | both train on 7,925 claims (124 providers) and score 4,561 (116 providers); 100 flagged each |
| Seed | 20260927 (byte-identical rebuilds) |

### Why a second dataset was needed

On a claim-header file 127 of the 164 checks cannot run: they need claim lines, prescriptions,
licences, approvals, payments, documents or policy tables that such a file does not have. Their
static classification in `rules/` is correct for that file and is **unchanged**. What changed is
that executability now also depends on the loaded file: a separately governed declaration in
`rules/unlocks/` says which tables unlock each check and which implementation then runs
(`src/fwa/engine/unlocks.py`, `src/fwa/engine/unlocked/`). The evaluator records, for every
check on every run, the catalogue classification, the effective one, and the basis
(`catalogue`, `unlocked` or `upgraded`). On the two claim-header files nothing unlocks and every
earlier figure is unchanged; `tests/governance/test_dataset_unlocks.py` enforces that, and that
an unlock can never alter a check's type, disposition, score or status.

### What was engineered, and why

* **A clean base population** (`tools/uae_demo/base.py`, `reference.py`): licensed and privileged
  clinicians on duty, active cover, approvals where required, tariff-priced lines with realistic
  copay, consistent pharmacy stock, remittances with ~5% denials, legitimate resubmissions. It is
  built so that, as far as possible, no check fires on it; the family authors measured each check
  on the clean base (almost all silent) before planting anything.
* **Planted patterns, one injector per family** (`tools/uae_demo/inject_*.py`): at least one
  realistic pattern for every scenario family (ANL through the model and composite; CLN, DOC,
  ENT, NET, PAY, PHR, POL through injectors) — upcoding, unbundling, duplicates, phantom
  services, services after death or after cover ended, unlicensed or on-leave clinicians,
  capacity breaches, agent–provider rings, prescription stacking, dispensing beyond stock,
  document alterations, resubmission gaming and more. Most injectors also plant **legitimate
  look-alikes** that a check's declared exclusion must clear, and the checks stay silent on them.
* **The answer key** (`data/uae_demo.strata.csv`, `.strata.json`) sits beside the dataset, never
  inside the folder or zip, and a static scan in the verifier and in the governance suite shows no
  detection code refers to it. Held-out evaluation labels (`evaluation_labels.csv`) are read only
  by the adapter's `held_out_labels`, for evaluation.

### What it does not do

* **One check cannot run:** NET-04-R01 needs reviewer-confirmed outcomes. Synthesising reviewer
  decisions would invent performance, so it is left not executable on purpose.
* **Six checks run but find nothing** here (CLN-05-R01, CLN-07-R02, ENT-03-R02, NET-04-R02,
  NET-04-R03, PHR-03-R03): claim-header checks whose pattern was not planted in this file.
  CLN-05-R01 (length of stay) compares a stay only with same-diagnosis claims *in the same care
  setting* when the file records one; before that change it compared inpatient stays with
  outpatient visits (length of stay 0) and raised 61 meaningless flags.
* **Four original claim-header checks exceed the 400-flag ceiling** on this file: NET-03-R01
  (1,236), PAY-06-R03 (1,155), PAY-10-R01 (640) and PAY-01-R03 (434). A multi-table file has many
  legitimate outpatient, lab and pharmacy claims per patient, provider, episode and diagnosis, and
  these checks were written for one-row-per-admission data. The ceiling routes their flags to
  watch-only, as designed, which is why most of the ~5,900 cases on this file are watch-only. The
  dedicated line-level checks cover the same ground on this file. Narrowing their comparison groups
  by care setting was tried and made them fire *more* (tighter groups), so it was reverted.
* **NET-03-R01** (repeated high-value patient–provider pair) is a claim-header check that
  over-fires on multi-table data, where one patient legitimately has many outpatient and pharmacy
  claims at one provider. Its flags exceed the per-check ceiling and are routed to watch-only, as
  the ceiling is designed to do. A line-level replacement is written
  (`net_03_r01_repeated_high_value_dyad_multitable`, 5 flags on clean data) but is not switched
  on, because the unlock mechanism only upgrades checks the catalogue classifies as simplified,
  and this one is classified fully executable. Reclassifying it is a catalogue decision.
* **Drift breaches.** The maximum feature PSI is about 5.5, driven by `admission_month` (18
  months do not split evenly across the calendar) and by expanding "prior history" features. That
  is real drift, correctly detected, and the models therefore stay in shadow on this file. It was
  not engineered away.
* **Half the claims are unscored by design.** The governed split trains on earlier claims from
  one half of the providers and scores later claims from the other half, so about half of all
  claims are in neither set. The Models page offers an **exploratory** "score every claim" view,
  clearly labelled and excluded from the promotion gate and every metric
  (`tests/governance/test_exploratory_scores_excluded.py`).

### Reproducing

```bash
python tools/make_uae_demo_dataset.py --out data/uae_demo --zip data/uae_demo.zip
python tools/verify_uae_demo_dataset.py
```

The build takes about 3–4 minutes; `--claims 1500` gives a small build for tests.

## The claim-header synthetic file (`claims_demo_synthetic.csv`)

`data/claims_demo_synthetic.csv` is a **synthetic** claim file, generated by
`tools/make_demo_dataset.py`, built for one purpose: to run every part of the
engine that an arbitrary claim-header extract leaves idle.

That idleness is not a hypothetical. A generic extract exercises the hard edits
and some of the peer statistics, and leaves the change-point detectors, the
duplicate and capacity controls, the novel-cluster discovery and — most
importantly — the entire promotion gate *in its passing state* undemonstrated.
A control that never runs and a control that runs and finds nothing look
identical from outside, and so do a gate that refuses correctly and a gate that
is broken shut.

| | `claims_demo_synthetic.csv` |
|---|---|
| Rows | 20,893 |
| Providers · members | 1,340 · 12,651 |
| Period | five whole years |
| Runnable controls firing | **37 / 37**, none silent |
| Signals → cases | 9,074 → 8,502 |
| Max feature PSI (drift) | **0.18 — warn**, against a 0.25 breach |
| Providers with a labelled claim | 49 / 1,340 (3.7%) |

## Read this before quoting any number from it

**A gate passed on a dataset built to pass it is a test of the gate, not
evidence about detection performance.** Every figure this file produces is a
property of a generator whose parameters sit in one Python module. Nothing here
transfers to real claims, and no number from it belongs in a sentence about how
well anything detects fraud.

What it is genuinely good for is the other half of testing a gate. A gate that
has only ever returned FAIL is indistinguishable from a gate that is broken
shut. This file shows the promotion path returning PASS when — and only when —
its conditions are actually met, which is the only way to know the criteria are
wired to anything.

The file names itself `_synthetic`, carries a warning in its sidecar
`.strata.json`, and is accompanied by a per-claim `.strata.csv` recording which
construction produced each row.

## What had to be engineered, and what that taught us

### 1. Drift: the inputs were never stationary

On an arbitrary extract both models fail the drift criterion outright, by an
order of magnitude rather than a margin. The cause is real and the detector is
right: the prior-history features are **expanding windows**.
A provider's "claims so far" is near zero at the start of the file and large at
the end, so the training and scoring periods genuinely hold different input
distributions.

The fix was not to relax the threshold. It was to build a population in which
those features are stationary:

- every provider, agent and member is active for a **bounded window**, and
  those windows are **staggered uniformly** across the file, so at any date the
  cross-section holds a stable mixture of entities at every stage of tenure;
- windows may start before the file opens and end after it closes, so the first
  and last months are not populated solely by entities at the extremes of their
  tenure;
- `days_since_policy_start` is drawn **independently of the service date**;
- the file spans **five whole years**, because `admission_month` is the month of
  the year and a 60/40 split only sees the same mix of months on both sides when
  each side spans whole years;
- source amounts inflate exactly as the governed FX table steps the rate down,
  so the AED value is stationary and the monitor is not reporting drift in the
  exchange rate as drift in anyone's billing.

Maximum PSI on the result: **0.18** — a warning, not a breach.

### 2. Lift: a signature the transparent composite cannot see

The composite scores providers on seven *provider-mean* metrics. The injected
anomaly touches none of them: it lives in four claim-level dimensions the
composite does not read — submission lag, insurers on the event, policy tenure
at service, cashless status — and appears on only a handful of a provider's
claims, so the provider's means stay at the peer median.

It is also **quantised into five recurring profiles** rather than spread along a
smooth gradient, so its far end has neighbours. A point with no neighbours gets
an enormous local-outlier-factor score, and one such point distorts every other
score in the file once min-max rescaling enters the picture.

Separately, a ring of 30 providers shares one modest, consistent profile —
pharmacy-heavy, approval below par, short stays. The composite averages over a
provider's claims and sees it easily; per claim it is unremarkable. The two
disagree about that group on purpose, and it is the composite that is right.

### 3. Calibration: only one model can pass, and that is provable

This is the finding worth keeping.

The calibration criterion min-max rescales the model score and compares it, bin
by bin, against the observed outcome rate. Summing the bins, the error can never
be smaller than the distance between the mean rescaled score and the overall
base rate:

```
ECE = Σ_b w_b · |mean(p)_b − mean(y)_b|  ≥  |mean(p) − base_rate|
```

Both models are scored against the **same** outcome series, so one base rate has
to serve both, and the best it can do is sit midway between the two means —
leaving each model at least half their separation:

```
max(ECE_isolation_forest, ECE_local_outlier_factor) ≥ |mean(p_IF) − mean(p_LOF)| / 2
```

On this data those means sit near **0.54** and **0.04** — the isolation forest's
measured ECE of 0.507 against a 3.7% base rate implies the first, and the local
outlier factor's 0.010 against the same base rate implies the second — so the
floor on the larger error is about **0.25** against a configured maximum of
**0.15**. No dataset closes that gap, because it depends on the two score
distributions' shapes under min-max rescaling and not on the labels at all.

Why the shapes differ: the isolation forest's score is bounded and roughly
symmetric, so rescaling leaves it near the middle. The local outlier factor is a
density ratio with one point more than three times beyond its 99th percentile —
in sixty-odd dimensions there is always such a point — and min-max keys the
entire scale off it.

So the base rate calibrates one model. It calibrates the **local outlier
factor**, because calibrating the isolation forest instead would require 54% of
providers to carry a confirmed fraudulent claim, a figure that would discredit
the file it appeared in. The result:

- `local_outlier_factor` — **PROMOTED**, all five criteria pass
- `isolation_forest` — four of five pass, including a lift of **2.2×**; it fails
  calibration alone, for the structural reason above

`tools/verify_demo_dataset.py` reproduces the whole verdict, and
`/tmp`-free reproduction of the bound is in the generator's docstring.

**If you want both models promoted**, one of these has to change, and each is a
decision rather than a fix:

1. **Rank-transform the score before comparing** (`p = rank / n` instead of
   min-max). That is what makes a calibration curve meaningful for an
   unsupervised score, and it would let both models be judged on the same
   footing. It changes the criterion.
2. **Raise `model_calibration_max_ece`** above that floor. This is the option the
   build brief explicitly warns against — *"do not tune until the model wins"* —
   and it should not be taken quietly.

Doing nothing is also defensible. The gate's own evidence text says a poor ECE
on an unsupervised score is expected; if that is true, the criterion is close to
unpassable by construction, and that is worth knowing about a gate that governs
promotion.

## How the labels were assigned, and why it is not circular

Labels are derived from model scores measured on an earlier, **unlabelled** pass
over the same file (`--calibrate`). Within each decile of the score, exactly the
expected number of providers is marked positive — matching the observed rate to
the stated confidence, which is the definition of calibration.

That is only legitimate because labels are genuinely held out of every feature
path, so adding them cannot change the scores. `tools/verify_demo_dataset.py`
asserts exactly that: it runs the engine on the file as shipped and again on a
copy with every label column removed, and requires the model scores to be
**identical**. They are, to the last bit:

```
✓ isolation_forest:     293 providers, largest score difference 0.00e+00
✓ local_outlier_factor: 293 providers, largest score difference 0.00e+00
```

If that check ever fails, the labelling is circular and the dataset is void. It
is the first thing the verifier prints.

## A defect this work uncovered

`DOC-02-R01` (cross-patient near-duplicate documents) could not fire on **any**
dataset. Its boilerplate stripper compiled the template patterns with
`re.DOTALL`, so `DISCHARGE SUMMARY.*` ran greedily from the first heading to the
end of the document and every document stripped to the empty string. Every token
set was empty, every document was dropped before comparison, and the control
returned nothing — silently, because a control that finds nothing looks exactly
like a control with nothing to find.

Fixed in `src/fwa/nlp/controls.py`, with regression tests in
`tests/unit/test_document_similarity.py` that assert on the stripped text rather
than on the signal count, since a signal count of zero was the symptom that hid
it for so long.

## Reproducing

```bash
python tools/make_demo_dataset.py --out data/claims_demo_synthetic.csv --calibrate
python tools/verify_demo_dataset.py data/claims_demo_synthetic.csv
```

The generator is seeded, so the file reproduces exactly. `--calibrate-to
isolation_forest` builds the other variant, at the base rate discussed above.

In the application: sign in as `analyst` or `admin`, open **Data**, paste the
path, and press *Run the engine on this file*. The **Models** page then shows
the promotion gate against this dataset.
